# M365/Entra/SharePoint Architecture Review Research

Authoritative-source research for reviewing DeltaSetup architecture drafts around GitHub Actions alerting, Entra monitoring/logging, Microsoft 365/SharePoint audit evidence, Enterprise Application assignment controls, and multitenant organization/cross-tenant sync.

## Key review bullets

- **GitHub Actions failure alerting:** GitHub Docs says users can enable email/web notifications for workflow runs they trigger and choose notification only when a run fails; scheduled-workflow notifications go to the workflow creator or the user who last changed/re-enabled the cron workflow. Treat this as a weak human-owned control: acceptance criteria should name the accountable recipient and include a periodic canary/screenshot showing failure notification delivery, plus a repository-level fallback such as branch protection/status checks or a workflow_run/webhook/issue-creation mechanism for shared visibility. Evidence: <https://docs.github.com/en/actions/concepts/workflows-and-actions/notifications-for-workflow-runs>.
- **Entra audit/sign-in/provisioning logs:** Microsoft Entra has three activity-log types: audit logs for tenant tasks, sign-in logs for user/client-app sign-in attempts, and provisioning logs for third-party/user provisioning actions. For review, require diagnostic settings that stream audit, sign-in, provisioning, risk, and service-principal-related categories to Log Analytics/Sentinel/Event Hub/storage; native portal/Graph access alone is only acceptable for short troubleshooting windows. Evidence: <https://learn.microsoft.com/en-us/entra/identity/monitoring-health/overview-monitoring-health>.
- **Alerting acceptance criteria:** Azure Monitor alerts require monitored resources, signals/data, conditions, and action groups; action groups support email/SMS/push, automation runbooks, Functions, Logic Apps, secure webhooks, Event Hubs, and ITSM. Acceptance criteria should verify alert rule definitions, action group owners, test-fired evidence, and documented suppression/processing rules. Evidence: <https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-overview>.
- **M365/SharePoint audit evidence:** Microsoft Purview unified audit log captures user/admin operations across Microsoft services; Audit Standard is enabled by default for eligible subscriptions and retains audit records for 180 days. Review drafts should not claim indefinite evidence unless Audit Premium/retention policies or export to SIEM/storage are explicitly implemented. Evidence: <https://learn.microsoft.com/en-us/purview/audit-solutions-overview>.
- **SharePoint drift controls:** Purview audit activities include file/page, sharing/access-request, site administration, and site permissions events such as `AnonymousLinkCreated`, `SharingPolicyChanged`, `HubSiteJoined/Unjoined`, `SiteCollectionAdminAdded`, `AddedToGroup`, and inheritance changes. Acceptance criteria should require saved audit queries or KQL for anonymous/company links, sharing policy changes, site collection admin changes, SharePoint group membership changes, and hub association drift. Evidence: <https://learn.microsoft.com/en-us/purview/audit-log-activities>.
- **Enterprise Application least privilege:** Entra application assignment supports direct user and group assignment; group-based assignment requires Entra ID P1/P2 and does **not** support nested groups. If “assignment required” is enabled, only directly assigned users or members of assigned groups can sign in. Review should reject nested-group assumptions and require explicit enumeration of direct app assignments. Evidence: <https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/assign-user-or-group-access-portal> and <https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/what-is-access-management>.
- **Direct assignment drift:** Direct app assignments are appropriate for break-glass or narrowly scoped exceptions, but are high drift risk for normal access. Acceptance criteria should prefer dynamic/named groups for business roles, require every direct user assignment to have owner, ticket, expiry/review date, and require periodic Graph export of `servicePrincipal/appRoleAssignedTo` as evidence.
- **Local-account bypass risk:** Microsoft warns that apps with local credentials or backup auth can allow retained access after Entra assignment removal and might not appear in Entra logs. Architecture drafts should require disabling local-account bypass, enforcing Entra SSO/Conditional Access, and using provisioning to disable/delete app-local accounts when out of scope. Evidence: <https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/what-is-access-management#preventing-application-access-through-local-accounts>.
- **MTO/cross-tenant sync:** MTOs define a boundary around organization-owned tenants; cross-tenant synchronization is one-way and automatically creates/updates/deletes B2B collaboration users. Cross-tenant access settings remain explicit per tenant-to-tenant relationship, and tenant admins stay in control. Acceptance criteria should show each inbound/outbound relationship, auto-redemption decision, sync scope, target `userType` choice, and deprovisioning behavior. Evidence: <https://learn.microsoft.com/en-us/entra/identity/multi-tenant-organizations/overview>.
- **MTO membership caveats:** Microsoft notes existing B2B collaboration member users in tenants that join an MTO immediately become MTO members, improved Teams collaboration relies on reciprocal B2B member provisioning, and M365 people search generally needs users shown in address lists plus `userType=Member`. Review should require pre-join inventory of B2B members and explicit cross-tenant sync scoping to avoid surprise visibility/access drift.
- **Break-glass:** Microsoft sources in this set repeatedly recommend least privilege and minimizing Global Administrator usage. For DeltaSetup, acceptance criteria should require at least two cloud-only emergency accounts excluded from brittle dependencies but monitored via sign-in alerts and reviewed in Entra audit/sign-in evidence.
